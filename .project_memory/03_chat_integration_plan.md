# План интеграции микросервиса Чат в Админ-панель

На основе изученной документации `docs/integration-admin-panel.md`, ниже представлен результат брейншторминга и оптимальные подходы к интеграции чата.

## 1. Архитектурный подход и Стейт-менеджмент

- **Авторизация:** Для всех REST-запросов (`/api/v1/chat/admin/*`) и WebSocket соединения (`/ws/chat?token=...`) используется **тот же самый токен**, что применяется для авторизации в текущей админ-панели (достается из `localStorage` по ключу `ACCESS_TOKEN_KEY`).
- **WebSocket соединение:** Необходимо создать глобальный контекст `ChatContext` (или использовать Zustand / Redux, если бы они были, но в проекте используется Context API + React Query). Глобальный провайдер будет устанавливать WS соединение при авторизации админа и слушать события `message.created` и `conversation.updated`.
- **Уведомления (Notifications):** При получении `message.created` в неактивном чате, система должна показывать всплывающее уведомление (Toast / Snackbar) и увеличивать счетчик непрочитанных сообщений в интерфейсе.
- **REST API:** Использовать `React Query` для загрузки списков диалогов (`GET /api/v1/chat/admin/conversations`) и истории сообщений (`GET .../messages`). Это даст хороший кеш и встроенные механизмы инвалидации.

## 2. Размещение в интерфейсе (UI/UX)

Для максимальной эффективности работы операторов рекомендуется **комбинированный подход**:

### Вариант А: Выделенная страница `/admin/chat` (Основной рабочий инструмент)
- **Сайдбар:** Добавить новый пункт меню "Чаты" / "Поддержка" в `SidebarMenu` (с использованием иконки `ChatTwoTone` или `SupportAgentTwoTone`). Возле иконки можно выводить бейдж (Badge) с количеством новых/неотвеченных чатов.
- **Лейаут страницы:** Классический двухпанельный интерфейс (Split View).
  - Слева: Список диалогов с вкладками "Мои (в работе)", "Очередь (неназначенные)", "Закрытые". Каждый элемент списка показывает иконку (Заказ или Поддержка), последнее сообщение и время.
  - Справа: Окно активного диалога с историей, кнопкой "Назначить на меня", полем ввода и кнопкой "Закрыть диалог".

### Вариант Б: Интеграция в Карточку Заказа `/admin/orders/:orderId`
- Так как чаты бывают типа `order`, на странице деталей конкретного заказа обязательно нужен блок или кнопка вызова чата.
- Если у заказа есть привязанный чат, оператор прямо со страницы заказа должен видеть историю переписки и системные сообщения об изменении статусов.

### Вариант В: Глобальный виджет / Индикатор в Header (Опционально)
- В верхней навигационной панели (Header) добавить иконку чата с Badge индикатором новых обращений. По клику — переход на страницу `/admin/chat`.

## 3. Рекомендуемый поэтапный план реализации

### Этап 1: Подготовка инфраструктуры (Слой данных)
1. Добавить `chat.ts` в `src/api/services/` с реализацией REST API методов (получение диалогов, сообщений, назначение, закрытие).
2. Создать класс или хук `useChatWebSocket` для управления WebSocket соединением (реконнекты, подписки, обработка типов `message.created`, `conversation.updated`).
3. Создать `ChatContext` для хранения глобального состояния (счетчик непрочитанных, активное соединение).

### Этап 2: Создание выделенной страницы Чатов
1. Создать роут `/admin/chat` и добавить его в `router.tsx`.
2. Добавить пункт в боковое меню `SidebarMenu`.
3. Сверстать `ChatSidebar` (список диалогов с вкладками и пагинацией).
4. Сверстать `ChatWindow` (отображение баблов сообщений: свои справа, чужие слева, системные по центру).
5. Реализовать поле ввода сообщений и отправку через WS/REST.
6. Добавить логику смены статуса (Кнопки "Взять в работу" / "Закрыть").

### Этап 3: Интеграция с заказами
1. На странице `OrderDetail` добавить секцию "Чат с клиентом".
2. Использовать переиспользуемый компонент `ChatWindow`, передавая туда `topic_id = orderId`.
